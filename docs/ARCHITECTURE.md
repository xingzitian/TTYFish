# 架构

三个独立模块，依赖方向单向：

```
        ┌───────────────────────────────────────────┐
        │  games/uno   （游戏：UNO）                 │
        │  engine/ 规则   ai/ 决策   ui/ 界面        │
        └───────────────┬───────────────────────────┘
                        │ 只依赖 sdk
        ┌───────────────▼───────────────────────────┐
        │  sdk   （契约，很小，第三方游戏也只依赖它） │
        │  Game 接口 · 客户端快照 · 界面小工具       │
        └───────────────▲───────────────────────────┘
                        │ 实现/消费
        ┌───────────────┴───────────────────────────┐
        │  hub   （平台）                            │
        │  sshd 接入 · room 房间 · web 账号 · store  │
        └───────────────────────────────────────────┘
```

规则只有一条：**箭头只能往上**。`sdk` 不认识 `hub`，`hub` 不认识 `uno`。
`hub` 在 `cmd` 里创建游戏挂载项，这是唯一的交叉点（房间集成测试会使用 UNO 验证行为）。

当前已完成通用挂载：`registry.Entry` 绑定游戏标识、`Game` 和 UI 工厂，
SSH 层通过 `UIContext` 提供会话依赖，不直接引用 UNO。
当前仍只挂载 UNO，尚未实现多游戏注册表和选游戏大厅。

---

## 1. 各模块职责

### sdk（契约）

| 内容 | 说明 |
|---|---|
| `game.Game` | 游戏要实现的方法集 |
| `game.Event` / `game.Phase` | 战报与阶段 |
| `client.Snapshot` | 平台的"玩家视角一帧"，游戏 UI 消费它 |
| `ui` 小工具 | 颜色深浅、宽度裁剪、面板拼接、按键表的通用部分 |

SDK 要小到"一个人一个下午能读完"。

### hub（平台）

| 包 | 职责 |
|---|---|
| `internal/sshd` | SSH 接入、公钥验签、会话分流（交互式 / exec auth） |
| `internal/room` | 房间、座位、托管、投票、聊天、时间线 |
| `internal/web` | HTTP、登录页、账号页、挑战轮询 |
| `internal/store` | SQLite：账号、凭证、会话、挑战、偏好 |
| `internal/registry` | 游戏挂载契约（Entry：标识 + Game + UI 工厂；多游戏查找待实现） |
| `cmd/hub` | 组装：读配置、开库、挂游戏、起 SSH 和 HTTP |

### games/uno（游戏）

| 包 | 职责 |
|---|---|
| `engine` | 纯规则：牌、状态、动作、裁剪、启发式机器人 |
| `ai` | 把局面翻译成提示词，问模型要一步 |
| `ui` | bubbletea 界面 |
| `game.go` | 把 engine 接成 `sdk/game.Game` |

## 2. SSH 入口的两种连接

平台只有一个 SSH 端口，靠"有没有 PTY / 有没有命令"分流：

```
连接进来
  ├── 有 PTY，无命令        → 交互式：进入 UNO（选游戏大厅待实现）
  ├── 无 PTY，命令 = auth X → 网页登录挑战
  └── 其它（scp / sftp / 探活）→ 直接拒绝，不进游戏
```

第三条很重要：MobaXterm 的文件侧栏会用同一个密钥开 exec 连接，
如果也当玩家处理，就会把正在玩的会话顶掉。这个坑踩过一次。

## 3. 一次交互的数据流

```
按键 ──► 游戏 UI（Model.Update）
          │ 产生一个动作（游戏自己的类型）
          ▼
        room.Act(指纹, 动作)
          │ 校验座位、交给 game.Apply
          ▼
        状态变化 ──► game.Observe(每个座位)
          │              │
          │              ├─► client.Snapshot{View any, 时间线, 玩家…}
          │              ▼
          └────────► 广播给该房间的所有订阅者
                         │
                         ▼
                  游戏 UI 渲染（把 View 断言回自己的类型）
```

平台全程不解释 `View` 的内容——它只是个 `any`。

## 4. 账号与登录的边界

以下为目标流程。当前交互式游戏仍使用公钥指纹作为座位身份、SSH 用户名作为昵称；
账号查找与自动建号目前接在网页 `auth` 路径，统一账号身份待实现。

```
SSH 握手
  └─ 公钥 + 签名 ─► sshd 验签 ─► 指纹
                       │
                       ├─ store.FindByIdentity(指纹)
                       │     有 → 用这个账号
                       │     没有 → 建号（TOFU）
                       ▼
                 账号{id, handle, 昵称}
                       │
                       ▼
                 游戏座位（昵称来自账号，不是 SSH 用户名）
```

网页登录（挑战）走的是同一条验签路径，只是额外做一件事：
把"这次签名是真的"这件事，和浏览器发起的那次登录绑在一起。

## 5. 部署拓扑

### 现在（单机）

```
systemd: hub
  ├── :2222  SSH   （玩家）
  └── :8080  HTTP  （浏览器，建议前面挂 Caddy 自动 HTTPS）
        │
        └── /var/lib/hub/hub.db (SQLite, WAL)
```

### 以后（分机，暂不做）

SSH 服务和 Web 服务拆开时，共享的是**账号数据库**，不是进程：

- 方案 A：Web 单独一机，账号库在那边；SSH 机通过内网 API 查身份（带缓存）
- 方案 B：读写分离，SSH 机只读副本

`store` 的接口按"可替换"设计：现在用 SQLite，以后换 Postgres 只改实现。

---

## 6. 为什么游戏不直接连数据库

- 游戏作者不该关心存储，也不该能读到别人的数据
- 平台要能"禁用某个游戏"而不删数据
- 需要持久化的游戏用平台给的键值接口：`store.KV(accountID, gameName).Get/Set`（规划接口，尚未实现）

---

## 7. 关键不变式

1. **信息裁剪只有一处**：`Observe`。界面、网络、AI 都从它取数据。
2. **平台不认牌**：`hub` 里不该出现任何游戏术语。
3. **座位与连接解耦**：断线只是座位没人操作，60 秒内回来还能接管。
4. **服务端权威**：客户端只发意图，合法性一律由游戏判定。
5. **验签唯一**：无论终端还是网页，认人只看"签名验证通过 + 指纹"。
